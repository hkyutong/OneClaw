# Why not just OpenClaw

You absolutely can use OpenClaw directly.

OneClaw exists because many users are not choosing between two runtimes.
They are choosing between:

- the upstream project
- a more productized way to adopt that project

## The short answer

Use **OpenClaw** if you want the upstream project as directly as possible.

Use **OneClaw** if you want the same self-hosted runtime category, but with:

- a clearer product story
- a macOS-first installer path
- Chinese-first onboarding and copy
- a more explicit Windows WSL2 and Linux deployment story
- more evaluation pages aimed at real assistant workflows

## Decision table

| Situation | Better starting point | Why |
| --- | --- | --- |
| You want the raw upstream project | OpenClaw | Closest to the source and latest upstream framing |
| You want the easiest productized entry point | OneClaw | Better onboarding and install-path guidance |
| You want the macOS GUI installer path | OneClaw | This is one of the main productized differences |
| You want the newest upstream changes first | OpenClaw | Upstream lands first there |
| You want Chinese-first product copy | OneClaw | This is a OneClaw focus area |
| You are contributing to the core runtime | OpenClaw | That is where the primary runtime evolves |

## What OneClaw changes

OneClaw mainly changes the adoption layer:

- packaging
- installer direction
- onboarding
- localization
- product framing

## What OneClaw does not change

OneClaw does **not** replace the core upstream runtime model.

It still depends on the same fundamentals:

- self-hosted gateway
- multi-channel messaging access
- sessions, tools, and routing
- browser UI and remote control surfaces

## The real tradeoff

The choice is usually not about technical possibility.
It is about **upstream freshness vs productized guidance**.

- OpenClaw wins if you want the most direct upstream path
- OneClaw wins if you want the easiest path to understanding, installing, and evaluating this category
